================================================ IOC =======================================================
IOC - Inversion Of Control
Normally if we need an object, we manually create it but with spring we do not need to.
Spring provides whatever object we need
Spring has IOC Container which contains objects of all classes, what object we need, it provides
Control has been given to spring, hence inversion of control

Application Context - Way to achieve IOC container. Both terms can be used interchangeably

Actually IOC container does not contain objects of all classes. It scans components.
We need to add annotation @Component to the classes which IOC should scan and keep with itself

@Component
class MyComponent{
    // class is automatically registered as a spring bean
}

Annotations can be used with, classes, interfaces, fields, methods

Beans - Objects in spring IOC container. More specifically singleton objects, shared within the full app.
They don't create problem since spring assumes they are stateless, no shared mutable state
If we use state then there will be inconsistencies, race conditions, concurrency problems

So no mutable shared state or proper synchronization

OR

Don't use singleton scope. Use these instead
@Scope("prototype") → new instance every time
@RequestScope → one per HTTP request
@SessionScope → one per user session

============================================== SpringBootApplication ============================================
@SpringBootApplication - class annotation, applied only once in the project, on the main class(class which has
main method).

Does work of 3 annotations:
@ComponentScan: Scans for beans to add into IOC Container
Important point, @Component classes can only be added to classes which are in the same package as @SpringBootApplicaton
package.
If we add components in class in some other packages, IOC container will not scan that class

com.app   <-- main class here
com.app.service
com.app.repo
this structure works

com.app.main        <-- main class
com.external.utils  <-- your "separate package"
this doesn't

So place main class at root package
com.app   <-- main class here
   ├── service
   ├── repo
   ├── util

Or manually define where to scan components
@SpringBootApplication
@ComponentScan(basePackages = {
    "com.app",
    "com.external.utils"
})
public class Application {
}

@EnableAutoConfiguration: Automatically uses configs. Ex if we use a DB(add it's dependency) and then ip port,
password in config then spring will use the configs and make connections and everything by itself, we don't
have to manually do things


@Configuration: class annotation. When used on a class, it indicates that the class will provide some configs

=================================================== Response Codes ==================================================
1. 1xx -> informational, rarely used

2. 2xx -> success
   200 -> OK, req successfully processed and server is returning the resource that it was asked for, GET
   201 -> CREATED, success and new resource has been successfully created, POST
   204 -> NO CONTENT, success but no response body, usually when there is nothing to be returned, DELETE

3. 3xx -> when client needs to take additional steps to get the resource
   301 -> resource moved permanently to new url. Client can cache the new url
   302 -> moved temporarily

4. 4xx -> client error
   400 -> bad request from client. Malformed req
   401 -> unauthorized. wrong password username.
   403 -> forbidden. no permission to access the resource for client

5. 5xx -> server side error
   500 -> internal server error. generic server side error message
   502 -> bad gateway. gateway server received bad response from upstream server
   503 -> service unavailable. server cannot process the req now due to overload or maintenance

==================================================== Transactions ================================================
@Transactional: method annotation. makes the method atomic. all or nothing
everything in the method should happen successfully as a single unit.
If any failure happens in between processing then everything that has been processed till now, should
be reverted back

@EnableTransactionManagement: added to the main class. tells spring to find all transactional methods.
Spring boot will make transactional context for every transactional method that it finds. A container that
will have DB operations related to that method and all will treat all of them as a single operation. Atomicity.
If any one of them fails, everything will be rolled back.

Isolation is also achieved. There will be separate transactional context(container) per request.

All of this is done by TransactionManager(an interface). Implemented by MongoTransactionManager(class by mongo).
Has methods like, commit, rollback, abort

==================================================== Spring Security ================================================
1. Spring security: framework used to handle authentication and authorization
2. Authentication: process of verifying a user's identity
3. Authorization: process of granting or denying access to specific resources or actions based on the authenticated
   user's role and permission (eg, admin role, read role)
4. By default, spring security uses HTTP Basic Authentication
5. HTTP basic authentication: the client sends an authorization header, Authorization: Basic<encoded-string>
   The server decodes the string, extracts the username and password, and verifies them.
   If they're correct, access is granted. Otherwise, an "Unauthorized" response is sent back.
6. Encoded string: credentials are combined into a string like, username:password which is then encoded using Base64
7. By default, all endpoints will be secured. Spring security will generate a default user with a random
   password that is printed in the console logs on startup.
9. username and password can also be configured in application.properties
   spring.security.user.name=user
   spring.security.user.password=password
10. spring security provides a default username, password for securing API endpoints.
    username: user, password: 6f2ee40e-9941-4146-b346-a49bcdb9a367, the password is printed on console when program starts
11. When you send request from postman, you can set, auth -> basic auth, add user name and password.
12. You can also add a header, Authorization, and for its value, go to any base64 encoder website, encode
    Basic username:password, and use this encoded value
13. Few problems with this approach:
        All endpoints have been secured, we can't decide which endpoints to secure, we may need some to be public
        Only one default user
14. @EnableWebSecurity: This annotation signals spring to enable its web security support. This is what makes your
    application secure. Used in conjunction with @Configuration. Helps customise spring security
15. WebSecurityConfigurerAdapter: A utility class in spring security. Provides default configs.
    Allows customisation of certain features. By extending it, you can configure and
    customise spring security for your application needs
16. configure method in WebSecurityConfigurerAdapter: This method provides a way to configure
    how requests are secured. It defines how request matching should be done and what security
    actions should be applied. Kia secure karna hai, kis tarah se karna hai.

-------------------------------------------------
configurations and methods in configure method
17. http.authorizeRequests(): this tells spring security to start authorizing the requests.
18. .antMatchers("/hello").permitAll(): this part specifies that HTTP requests matching the path
    /hello should be permitted(allowed) for all users, whether they are authenticated or not
            Permits all requests to /hello without authentication
19. .anyRequest().authenticated(): this is a more general matcher that specifies any request
    (not already matched by previous matchers) should be authenticated, meaning users have to provide
    valid credentials to access these endpoints
              Any other requests need to be authenticated and a form-based login will be used.
20. .and(): this is a method to join several configurations. It helps to continue the configuration
    from the root(HttpSecurity)
21. .formLogin(): this enables form-based authentication. By default, it will provide a form for the
    user to enter their username and password. If the user is not authenticated and they try to
    access a secured endpoint, they'll be redirected to the default login form.

22. You can access /hello without any authentication. However, if you try to access another endpoint,
    you'll be redirected to a login form.
23. When we use the .formLogin() method in our security config without specifying
    .loginPage("/custom-path"), the default login page becomes active.
24. Spring security provides an in-built controller that handles the /login path.
    This controller is responsible for rendering the default login form when a GET
    request is made to /login.
25. By default, spring security also provides logout functionality. When .logout() is
    configured, a POST request to /logout will log the user out and invalidate their session.

26. Basic authentication, by its design, is stateless. Username and password must be sent along
    with every request
27. Some applications do mix basic authentication with session management for various reasons.
    This isn't standard behaviour and requires additional setup and logic. In such scenarios,
    once the user's credentials are verified via basic authentication, a session might be established
    and the client is provided a session cookie. This way the client won't need to send the
    authorization header with every request, and the server can rely on the session cookie to identify
    the authenticated user.
28. When you log in with spring security, it manages your authentication across multiple requests, despite
    HTTP being stateless.

    a. Session creation: after successful authentication, an HTTP session is formed. Your authentication
       details are stored in this session.
    b. session cookie: A JSESSIONID cookie is sent to your browser, which gets sent back with subsequent
       requests, helping the server recognize your session
    c. SecurityContext: Using the JSESSIONID, spring security fetches your authentication details for each request.
    d. Session Timeout: Sessions have a limited life. If you're inactive past this limit, you're logged out.
    e. Logout: When logging out, your session ends, and the related cookie is removed.
    f. Remember me: Spring security can remember you even after the session ends using a different
       persistent cookie(typically have a longer lifespan).

    In essence, spring security leverages sessions and cookies, mainly JSESSIONID, to ensure you
    remain authenticated across requests.


29. We want our spring boot app to authenticate users based on their credentials stored in mongoDB database.
    This means that our users and their passwords(hashed) will be stored in mongo, when a user tries to login,
    the system should check the provided credentials against what's stored in the DB.

30. csrf: Cross Site Request Forgery. Enabled by default in spring security, spring expects in req we will send
    a csrf token too. Not necessary when requests are stateless

=================================================== Profiles ===================================================
1. Different configs for dev, prod, etc
2. make diff yml files for different profile, eg, application-dev.yml
3. in application.yml(default profile uses this), set this prop, spring.profiles.active: dev
4. if there are common configs in different ymls, we can set it only once in application.yml, no need to set
   separately in different profiles
5. But in prod we can't change profile manually, then commit, then make jar
   we can give property while running jar, java -jar <jar-name> --spring.profiles.active=dev
6. For making jar with maven, which includes test files, we have to first run mvn clean, with additional properties
   mvn clean package -D spring.profiles.active=dev
   -D specifies system property
   If there were no test classes, we could have simply written, mvn clean package
7. Can also have different configs based on profiles too, @Profile("dev"), class level annotation, like used
   in SpringSecurity class.
   Basically make beans based on profiles
8. can add multiple profiles in active profiles, separated by comma


=================================================== Logging=========================================================
1. Frameworks for logging:
    a. Logback: spring boot default. Flexible configuration and good performance
    b. Log4j2: advanced features like asynchronous logging
    c. Java Util Logging(JUL): java default. less features. part of jvm. if you need to upgrade this framework
       then need to update jvm

2. To customise logback configs, make logback.xml in src/main/resources
3. Logging levels: TRACE, DEBUG, INFO, WARN, ERROR
4. @Slf4j: class annotation, automatically makes logger instance, else we would have to manually write something like,
    private static final Logger logger = LoggerFactory.getLogger(UserService.class);
5. We can define logging levels, check yaml. If we define a level, only those level logs and more severe than those
   will get printed. Severity level: TRACE < DEBUG < INFO < WARN < ERROR
   So if level is set to WARN then only warn and error logs will be printed
6. log levels can be defined per package level
7. log level can also be defined as root, everything will use that log level, even spring internal libs
   logging.level.root: ERROR
8. can also turn off logging, logging.level.root: OFF
9. logging levels can be defined at class level too, just give the class name
    logging.level.net.engineeringdigest.journalApp.service.UserService: OFF
10. logging levels can also be defined in xml, logback.xml, check the file to see how to write the configs
